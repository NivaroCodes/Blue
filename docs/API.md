# Blue frontend API contract v1

Основан на MVP-плане команды. В ветке `codex/live-ingestion-safe` этот контракт реализован опубликованным backend; локальный режим frontend по-прежнему поддерживает синтетическое демо.

Все запросы идут на `{baseUrl}/api`. `baseUrl` задаётся конфигурацией `VITE_API_BASE_URL` (пользовательский UI не содержит адреса сервиса); пустой адрес означает текущий origin. В Vite `/api` проксируется на `API_PROXY_TARGET` (по умолчанию `http://127.0.0.1:8000`). Время передаётся в ISO 8601 с часовым поясом; интерфейс показывает UTC+5. Идентификаторы — строки. JSON-ответы проверяются Zod.

## GET /api/alerts

В режиме «Рабочие данные» frontend исключает серверные демозаписи: источник `blue_demo_synthetic_v1`, идентификаторы сообщений `synthetic-v<номер>-<номер>`, явный префикс `[SYNTHETIC / ВЫМЫШЛЕННЫЕ ДАННЫЕ]` и необязательный флаг `is_synthetic: true`. Флаг `is_synthetic: false` или отсутствие флага сохраняют обратную совместимость; известные маркеры демонабора всё равно исключаются. Обычное упоминание слова «synthetic» в сообщении не является основанием для фильтрации.

Сводка рабочего интерфейса рассчитывается по этому же полному отфильтрованному snapshot, поскольку серверный `/api/stats` может включать демосид. Прямое открытие синтетической записи через frontend также блокируется. Записи в базе не удаляются, backend API сохраняет прежний контракт. Локальный деморежим frontend работает отдельно и по-прежнему доступен явно через настройки.

Возвращает массив `Alert` или `{ "items": [Alert, ...] }`. По умолчанию `visibility=main`: сообщения `OFF_TOPIC` исключены из основной очереди. `visibility=off_topic` возвращает только скрытые сообщения, `visibility=all` — все. Frontend загружает `visibility=all` и разделяет очереди локально, чтобы обеспечить поиск, фильтры и пагинацию в обеих вкладках. Query `level=HIGH` сохраняется; если понадобится серверная пагинация, сначала расширьте контракт.

```json
{
  "id": "alert_104",
  "platform": "telegram",
  "chat_id": "demo_01",
  "chat_name": "Демонстрационная группа",
  "message_id": "msg_104",
  "sender_hash": "user_hash_23",
  "text": "Вложи 5000 тг — получи 10000 завтра!",
  "timestamp": "2026-10-22T10:00:00+05:00",
  "status": "PROCESSED",
  "risk_score": 82,
  "risk_level": "HIGH",
  "reasons": [
    { "code": "UNREALISTIC_RETURN", "evidence": "получи 10000 завтра" },
    { "code": "MONEY_REQUEST", "evidence": "Вложи 5000 тг" }
  ],
  "explanation": "Есть обещание быстрой высокой доходности и запрос вложений. Нужна ручная проверка.",
  "confidence": 0.84,
  "review_status": "NEW",
  "reviewer_note": "",
  "model_version": "analyzer-v1"
}
```

Формат `Alert` объединяет сообщение и анализ в плоский JSON. Backend может хранить их в отдельных таблицах. Пример оценки демонстрационный.

Обязательны `id`, `platform`, `chat_id`, `chat_name`, `message_id`, `sender_hash`, `text`, `timestamp`, `status`. Для `PROCESSED` и `OFF_TOPIC` также обязательны ненулевые `risk_score` и `risk_level`.

### Требования к качеству поля `explanation`:
Заключение формируется на основе объективных признаков и презумпции невиновности:
1. Исключены тавтологии и плеоназмы («классические признаки классической...», «гарантированная гарантия»).
2. Запрещены безапелляционные суждения о виновности или уголовном преступлении («автор — мошенник», «доказано мошенничество»); квалификация даётся исключительно в терминах рисков и признаков недобросовестных финансовых схем.
3. Разделены факты (точные цитаты, реквизиты, условия) и аналитическая оценка.
4. Рекомендации носят сугубо аналитический характер (проверка реквизитов по базам АРРФР/АФМ, запрос лицензии, аудит сетевых связей, ручная верификация); карательные команды («немедленная блокировка») запрещены.

- `platform`: `telegram` или `whatsapp`.
- `status`: `PENDING`, `PROCESSING`, `PROCESSED`, `ERROR`, `OFF_TOPIC`. Последний означает обратимое исключение из основной очереди; анализ, исходный текст и решение аналитика сохраняются.
- `risk_score`: число 0–100 либо null для незавершённого анализа.
- `risk_level`: `LOW`, `MEDIUM`, `HIGH` либо null. Стартовые пороги: 0–29 / 30–59 / 60–100; backend отвечает за согласованность уровня и score:
  - **HIGH (60–100)**: зафиксировано несколько взаимосвязанных подозрительных признаков финансовых рисков, требующих аналитической проверки (не означает юридически доказанное мошенничество или совершение преступления).
  - **MEDIUM (30–59)**: выявлены неоднозначные, изолированные или противоречивые признаки (серая зона, рекомендован мониторинг).
  - **LOW (0–29)**: в предоставленных данных известные признаки рисков не обнаружены (не означает доказанную абсолютную безопасность контента).
- `reasons`: массив `{code, evidence}`. Evidence — точная подстрока исходного текста. Неизвестные коды показываются без потери значения. Если фрагмент не найден, он остаётся в списке причин, но не выделяется в исходном тексте.
- `confidence`: число 0.0–0.95 либо null. Эвристический показатель однозначности оценки и достаточности доступного контекста для вынесенного вердикта (некалиброванная эвристическая мера; не является статистически калиброванной вероятностью безошибочности или юридическим выводом о виновности; искусственно не завышается до 1.0).
  > **Важно**: показатель `confidence` ортогонален категории `risk_level` и **не предназначен для определения уровня риска**. Одинаковые значения `confidence` (например, 0.75–0.80) естественны для разных уровней риска: длинный нейтральный текст (`LOW`) и сообщение с одним зафиксированным признаком (`HIGH`) одинаково однозначны для анализа в рамках своих вердиктов. Категория риска определяется исключительно шкалой `risk_score` и факторами `reasons`.

  Ориентировочные примеры (типичные бенчмарки) достаточности контекста, согласованные с кодом:
  - **HIGH (при 2 и более подтверждённых признаках)**: ориентир **0.85–0.95** (высокая фактологическая база взаимно подтверждающих сигналов).
  - **HIGH (при 1 изолированном признаке)**: ориентир **0.70–0.80** (выраженный сигнал при ограниченном контексте).
  - **MEDIUM (серая зона)**: ориентир **0.45–0.65** (повышенная неопределенность из-за противоречивых или изолированных условий; требуется аналитик).
  - **LOW (нормальный информативный контекст)**: ориентир **0.70–0.85** (достаточный объем текста >= 15 символов, >= 3 слов для уверенного исключения известных признаков; базовый 0.80).
  - **LOW (фрагментарные данные)**: ориентир **0.30–0.45** (базовый **0.35**; короткие реплики < 15 символов или < 3 слов, где данных недостаточно для категоричного исключения рисков).
  - **Незавершённый анализ / ошибка (null)**: для статусов `PENDING`, `PROCESSING`, `ERROR`.
- `review_status`: `NEW`, `REVIEWED`, `FALSE_POSITIVE`.
- Необязательные поля: `reasons` → `[]`, `explanation` / `reviewer_note` → `""`, `model_version` → `"Не указана"`, `confidence` → null, `review_status` → `NEW`.

Для PENDING / PROCESSING / ERROR возвращайте `risk_score: null`, `risk_level: null`, `confidence: null`, `reasons: []`. Frontend не допускает review до PROCESSED. Сырые персональные идентификаторы отправлять не нужно — используется `sender_hash`.

## GET /api/alerts/{id}

Возвращает один `Alert` в том же формате. Для неизвестного id — HTTP 404. Маршрут должен поддерживать открытие прямой ссылки и перезагрузку страницы.

## GET /api/stats

```json
{
  "total_messages": 31,
  "pending": 1,
  "processing": 1,
  "errors": 1,
  "off_topic": 0,
  "by_level": { "HIGH": 12, "MEDIUM": 9, "LOW": 7 }
}
```

Все числа неотрицательные, счётчики целые. `by_level` включает только обработанные записи основной очереди. Для согласованного snapshot: `total_messages = HIGH + MEDIUM + LOW + pending + processing + errors + off_topic`. Скрытые записи не считаются ошибками анализа.

Статистика по чатам, платформам и признакам рассчитывается frontend по загруженному массиву `/alerts`. Так обе команды могут закончить MVP без дополнительного endpoint.

Источник определяется парой `(platform, chat_id)`: одинаковые `chat_id` в Telegram и WhatsApp допустимы и не объединяются. Ссылки на выборку источника содержат оба фильтра. Лента и аналитика используют время последней успешной загрузки как общую границу периода; сообщения с датой позже этой границы исключаются из временной выборки. На паузе граница остаётся прежней до следующей загрузки.

## POST /api/alerts/{id}/review

```json
{
  "review_status": "FALSE_POSITIVE",
  "reviewer_note": "Оплата за обучение, обещаний прибыли нет."
}
```

`review_status` — NEW / REVIEWED / FALSE_POSITIVE. `reviewer_note` — строка до 2000 символов. Ответ 200 — полный обновлённый `Alert`. Ошибки 4xx/5xx показываются в форме, без ложного сообщения об успешном сохранении. Backend должен валидировать запрос, авторизовать аналитика перед реальным использованием и сохранять решение.

## POST /api/alerts/{id}/visibility

Требует той же авторизации аналитика, что и чтение сообщений. JSON `{ "off_topic": true }` скрывает одно проанализированное сообщение из основной очереди, `{ "off_topic": false }` восстанавливает его. Ответ 200 — полный обновлённый `Alert`; 404 — запись не найдена; 409 — анализ ещё не завершён. Действие меняет только `messages.status` между `PROCESSED` и `OFF_TOPIC`; текст, оценка модели, изображение и история проверки не меняются. Для изменения решения аналитика скрытое сообщение сначала восстанавливают.

## Live и ошибки

Frontend опрашивает `/alerts` и `/stats` параллельно, затем ждёт 10 секунд до следующего цикла; конкурирующих циклов одного подключения нет. Таймаут 12 секунд. При смене адреса или режима старые запросы отменяются. Оба ответа должны пройти валидацию, прежде чем новый snapshot попадёт в интерфейс. При ошибке уже загруженные данные остаются с отметкой сбоя; автоматической подмены демо нет. Пауза оставляет возможность ручного обновления.

После успешного сохранения решения ответ snapshot, запрошенного до сохранения, отбрасывается: он не должен возвращать прежний статус и сбрасывать форму. Следующий цикл загружает актуальные данные и продолжает принимать изменения других аналитиков. Ошибка автообновления показывается также на странице проверки сообщения, с сохранением загруженного текста и возможностью повтора.

В production frontend входит через Supabase Auth и передаёт его access token как `Authorization: Bearer ...` на защищённые маршруты `/api`. Backend проверяет токен через Supabase Auth; без него чтение и сохранение решения возвращают HTTP 401. `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` публичны и встраиваются в frontend; ключ `SUPABASE_SECRET_KEY` там запрещён. При отдельном backend задайте `CORS_ORIGINS` точным origin сайта.

## POST /api/messages

Относится к backend-пайплайну. Требует серверный `Authorization: Bearer <INGEST_API_TOKEN>`; пользовательский Supabase access token не подходит. Тот же токен нужен для `POST /api/analyze-image`. Telegram и WhatsApp поступают через отдельные webhook с их собственными проверками. Dashboard не вызывает ingestion; кнопка «Демо-сообщение» только добавляет синтетическую запись в память браузера и не запускает AI. В демо решения хранятся локально, а в API-режиме данные и решения хранятся сервером.
